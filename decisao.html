1. As correções de acessibilidade

Nesta seção são registradas as correções de acessibilidade realizadas durante a Atividade 06.

Registro das correções de acessibilidade
Componente Problema Como se detectou Correção Onde está no código
Botão do menu responsivo O modelo da documentação exibe um rótulo de acessibilidade em inglês, o que diverge do idioma padrão aplicado na página. A verificação dessa nomenclatura foi realizada na aba de Acessibilidade (Accessibility) do Chrome DevTools, inspecionando a propriedade Name. Inseriu-se o atributo aria-label="Menu" para garantir que o elemento pudesse ser reconhecido e lido em português. A alteração foi feita no documento catalogo-bootstrap.html, diretamente no elemento button que possui a classe navbar-toggler.
Botão de fechar o diálogo O código de referência traz a marcação aria-label definida como "Close", não acompanhando o idioma utilizado na página. A constatação foi feita ao examinar o elemento através da aba Accessibility do Chrome DevTools, avaliando o valor contido em Name. Foi atribuído o valor aria-label="Fechar", assegurando que a leitura e a identificação do componente ocorram em língua portuguesa. O ajuste foi realizado no documento catalogo-bootstrap.html, mais precisamente no botão de classe btn-close que fica na parte superior da janela modal do Açaí médio.
Hierarquia de títulos na janela modal O modelo fornecido pela documentação emprega a tag <h1> para o cabeçalho do modal, o que gera um problema semântico, visto que a página já conta com um título principal de mesmo nível. A inconsistência foi notada ao confrontar o código com as diretrizes do Bootstrap e ao revisar a estrutura lógica dos cabeçalhos do documento. A tag foi trocada por <h2 class="modal-title h5">, o que ajusta a ordem semântica dos títulos sem causar impacto no visual do elemento. A modificação encontra-se no documento catalogo-bootstrap.html, especificamente no bloco modal-header pertencente à janela de detalhes do Açaí médio.
Associação de mensagens de erro Os alertas de falha eram visíveis na interface gráfica, mas não possuíam vínculo semântico com os seus respectivos campos na árvore de acessibilidade. O apontamento foi feito com base nas orientações da seção 2.10 da apostila, aliado à inspeção do input de E-mail através da aba Accessibility do Chrome DevTools. A solução adotada foi incluir o atributo aria-describedby nos três campos obrigatórios, conectando-os aos atributos id que foram inseridos nos textos de alerta. As adequações ocorreram no documento checkout-bootstrap.html, atuando diretamente nos campos de nome, email e termos, para ligá-los às mensagens que receberam os identificadores nome-erro, email-erro e termos-erro.
Identificação semântica do diálogo Embora a tag <div> do modal faça uso do atributo aria-labelledby, faltava a definição semântica explícita caracterizando o componente como um diálogo no HTML estático. A constatação baseou-se nas orientações presentes no roteiro da Atividade 06, em conjunto com a necessidade de prevenir apontamentos de erro na ferramenta de validação de HTML. A solução implementada foi inserir o atributo role="dialog" na estrutura principal (elemento contêiner) da janela modal. A modificação foi inserida no documento catalogo-bootstrap.html, incidindo especificamente sobre a tag <div class="modal fade" id="detalhe-acai">.

Pendências de acessibilidade

  1. Foco após validação do formulário: ao submeter o formulário com informações incorretas, o foco permanece no botão "Fazer pedido". O comportamento ideal exigiria a implementação de um script que movesse o foco automaticamente para o primeiro input inválido, agilizando a correção por parte do usuário.
  2. Janela modal restrita a um único produto: atualmente, o botão “Ver detalhes” funciona exclusivamente para o item do Açaí. Para contemplar os demais, faria-se necessário desenvolver uma lógica de programação capaz de atualizar o conteúdo do diálogo de maneira dinâmica, dependendo da opção selecionada no catálogo.

2. O registro de decisão

Contexto

O projeto AgroFeira precisa definir qual abordagem de estilização será adotada para a sua futura aplicação em React. Durante as análises de desempenho, constatou-se que o CSS autoral transferiu apenas 5,5 kB, enquanto o Bootstrap exigiu a transferência de 35,0 kB de CSS e acrescentou um peso de 25,2 kB de JavaScript. Além do tamanho maior, notou-se uma forte dependência desses scripts: ao desativar o JavaScript no navegador, o menu responsivo e a janela de diálogo deixaram de funcionar, além disso, o formulário de checkout passou a permitir o envio de campos vazios, pois sua validação também depende de JavaScript. Esses resultados fundamentam a escolha final.

Opções consideradas

  1. CSS autoral: garante maior controle sobre a aparência e personalização dos elementos da AgroFeira, porém demanda um trabalho significativamente maior para desenvolver, organizar e manter os estilos de forma manual. Como reflexo disso, na Atividade 05, essa estratégia contabilizou 530 linhas de CSS, resultando em uma transferência de 5,5 kB.
  2. Bootstrap: acelera a construção de interfaces responsivas ao fornecer componentes e classes pré-configuradas, minimizando a necessidade de escrever CSS manualmente. Em contrapartida, insere dependências externas e eleva o volume de dados transferidos, o que fica evidente nos números: embora o projeto tenha exigido apenas 84 linhas de CSS personalizado na Atividade 05, o framework demandou a transferência de 35,0 kB de CSS, somados a um acréscimo de 25,2 kB de JavaScript registrado na Atividade 06.
  3. Tailwind: viabiliza a criação de interfaces flexíveis através da aplicação de classes utilitárias diretamente no HTML, o que facilita muito a personalização. Em contrapartida, exige que o desenvolvedor organize e combine essas classes manualmente para estruturar os elementos, em vez de fornecer componentes visuais já prontos como o Bootstrap. Conforme apresentado nos slides da Aula 06, o framework pode ser testado em ambiente de desenvolvimento utilizando o Play CDN, porém não chegou a ser implementado ou medido nas atividades do projeto AgroFeira.

Decisão

Considerando que o CSS autoral exigiria um alto esforçocontínuo de desenvolvimento e manutenção, e que o Tailwind demandaria uma curva de aprendizado para a construção manual de componentes através de classes utilitárias, optei por seguir com o Bootstrap completo, utilizando tanto a sua folha deestilos quanto o seu JavaScript, para aproveitar a agilidadedos componentes prontos e a redução drástica na escritade código personalizado.

Consequências aceitas

Ao optar pelo Bootstrap completo, assumo o custo do maior volume de dados transferidos, considerando os 35,0 kB de CSS e os 25,2 kB de JavaScript medidos nas atividades. Também assumo a dependência do JavaScript do Bootstrap, sabendo que o menu responsivo e a janela de diálogo deixam de funcionar quando ele está desativado. Além disso, reconheço o risco de possíveis conflitos futuros com React, uma vez que o JavaScript do Bootstrap altera diretamente classes e atributos do HTML, podendo interferir no gerenciamento da interface realizado pela biblioteca React.

O que me faria mudar de ideia

Eu reconsideraria a utilização do Bootstrap completo caso fossem detectados conflitos críticos entre a manipulação direta do HTML feita por seu JavaScript e o gerenciamento de interface do React. Além disso, a decisão seria revista se futuras medições apontarem que o peso adicional dos arquivos prejudica de forma significativa o tempo de carregamento da aplicação, ou se a necessidade constante de sobrescrever e adaptar os estilos originais se tornar tão custosa que anule a principal vantagem de adotar um framework de componentes prontos.
